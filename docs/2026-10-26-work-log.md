## 程序现在怎样执行

```text
main
  ├─ 配置握手、解码器及 OnPeer
  ├─ NewTCPTransport：创建 rpcch
  ├─ 启动消费 goroutine，等待 Consume() 返回的 channel
  └─ ListenAndAccept：监听 :3000
       └─ acceptLoop：等待客户端
            └─ handleConn
                 ├─ 注册 defer，退出时关闭连接
                 ├─ HandshakeFunc：当前为空握手
                 ├─ OnPeer：当前 main 中的 Onpeer 会立即关闭连接
                 └─ 循环解码 → 设置来源 → rpcch 发送 → 主程序消费
```

注意：图中最后一条是设计中的正常收消息路径。当前示例回调会提前关闭连接，所以客户端即便连接成功，随后也无法按预期继续传输消息。

## 今天需要理解的几个概念

### 无缓冲 channel 与 nil channel

```go
rpcch: make(chan *RPC)
```

这创建的是无缓冲 channel，发送与接收需要配合完成。它不是“提前留出缓存”，也不保证发送方永不阻塞。只有 `make(chan *RPC, 10)` 这样的写法才带容量，但添加缓冲仍不能代替消息所有权和退出机制设计。

如果只声明 `rpcch chan *RPC` 而没有 make，其值是 nil，对它发送和接收都会永久阻塞。本次代码已补上初始化。

### Consume 的只读接口

```go
func (t *TcpTransport) Consume() <-chan *RPC
```

`<-chan *RPC` 表示调用方只能接收。这个方法返回同一个内部 channel，不会每次创建新 channel。当前 main 用 `msg := <-tr.Consume()` 阻塞等待数据；未来若增加 channel 关闭机制，应同时调整消费循环，避免收到零值后不断打印。

### 握手与 OnPeer 的职责

握手用于在读取业务消息前检查连接；当前空握手直接放行。`OnPeer` 是握手后的可选扩展点，可以登记节点或决定拒绝连接。它不应在希望继续通信时无条件关闭连接。

### defer 与错误变量遮蔽

`defer` 只有在当前函数退出或栈展开时才执行；如果处理函数卡在 channel 发送处，defer 尚不会关闭连接。

函数外层的 `var err error` 与读取循环中的 `err := ...` 是两个不同变量。延迟日志读取的是外层 err，因此当前日志可能遗漏实际的读取错误，出现 nil 的格式提示。后续应统一错误变量或在对应错误分支记录原因。

### 指针消息不等于独立消息

channel 发送 `*RPC` 时传递的是指针，不会自动复制结构体。当前 RPC 在循环外创建，下一次解码会改写同一个对象；消费者即使已经收到指针，也可能还在读取它。后续应每轮分配独立 RPC，并明确负载数据的所有权。

## 今天的运行与排查提示

在项目根目录执行：

```bash
make run
```

另开终端检查监听与连接：

```bash
lsof -nP -iTCP:3000 -sTCP:LISTEN
nc -v 127.0.0.1 3000
```

当前 `Onpeer` 会主动关闭连接，因此连接后很快退出，不代表 `nc` 指令写错。若要继续练习消息接收，下一步可把示例回调调整为仅返回 nil，或者不配置 `OnPeer`；这是建议，当前注释版本尚未修改该行为。

回调调整后，可尝试向默认解码器发送文本：

```bash
printf 'hello\n' | nc -w 1 127.0.0.1 3000
```

该命令针对 `DefaultDecoder`；切换 Gob 后必须发送 Gob 数据。即使单条文本收到，也不能证明连续消息与并发消息正确，仍需修复消息对象复用并补测试。

停止程序：点击正在运行服务的终端，按 **Control+C（⌃C）**。出现 shell 提示符表示前台程序已结束。使用 `make run` 时显示 `Interrupt` 属于正常中断信息。

如果测试监听失败，先检查端口是否正被自己运行的 `fs` 占用。当前测试也固定使用 3000 端口，应停止服务后再运行测试；长期应把测试改成 `127.0.0.1:0`，让系统分配空闲端口。
