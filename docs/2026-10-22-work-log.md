## 本次简介

在第一次完成 TCP 监听和连接接收的基础上，本次进一步实现了消息读取，并通过 Mac 终端的 `nc` 命令验证了文本数据接收流程。代码从“能接收连接”推进到了“能读取数据、记录来源并打印消息”的阶段。

## 消息接收流程

```text
Mac 终端发送字节
  → 服务端 Listener.Accept() 接收连接
  → 启动 handleConn(conn)
  → 执行 HandshakeFunc
  → DefaultDecoder 从连接读取字节
  → 保存到 Message.PayLoad
  → 使用 conn.RemoteAddr() 设置 Message.From
  → 在服务端终端打印消息
```

`Accept()` 在没有客户端时阻塞等待；建立连接后，读取操作也可能阻塞等待数据。启动时没有输出，不代表程序没有运行。当前服务端没有实现 echo，因此客户端不会自动收到回复。

## Mac 终端验证方法

在项目根目录启动服务端：

```bash
make run
```

在另一个终端检查监听：

```bash
lsof -nP -iTCP:3000 -sTCP:LISTEN
```

向当前默认解码器发送普通文本：

```bash
printf 'hello\n' | nc -w 1 127.0.0.1 3000
```

这里发送的是 `hello` 和一个换行符。该命令适用于主程序当前配置的 `DefaultDecoder`；切换为 `GOBDecoder` 后，需要发送 Gob 编码数据。

本次终端截图已观察到消息内容及来源地址。`PayLoad` 的 `[104 101 108 108 111 10]` 对应 `hello\n`；`[::1]:54392` 中的 `::1` 是 IPv6 本机回环地址，后面的端口是客户端临时端口，每次连接可能不同。

## 本次理解与排查的问题

- **连接与消息是两个步骤。** `nc` 建立连接后，不会自动构造 Go 的 `Message`；服务端需要读取数据并填充消息字段。
- **编码格式必须一致。** 普通文本可以由默认解码器读取，Gob 解码器需要符合 Gob 格式的数据。
- **字节与文字的显示不同。** 打印整个结构体时，字节切片可能显示为数字；如需展示文字，可以使用 `fmt.Printf("TCP 收到消息：%s\n", msg.PayLoad)`。
- **来源地址需要显式设置。** 未赋值时 `From` 为 nil；读取后使用 `conn.RemoteAddr()` 记录发送方。
- **日志参数需要匹配格式。** 用 `%s` 打印整个连接对象会出现异常格式提示；连接日志可以改为打印 `conn.RemoteAddr().String()`，这项日志调整尚未写入当前代码。
- **读取失败后应结束当前处理。** 当前已将解码错误后的 `continue` 改为 `return`，避免客户端断开后持续读取并打印 EOF；连接资源的关闭还需完善。

当前 `DefaultDecoder` 每次读取最多 1028 字节，没有定义消息边界。TCP 是字节流，一次发送不保证对应一次读取，因此当前验证只说明小段文本能被读取，尚不能保证完整消息划分。

当前 `GOBDecoder` 每次调用都重新创建 Gob Decoder，连续消息可能丢失解码状态，后续应改为每条连接独立持有并复用 Decoder。
